# Current System Architecture

## 1. Architecture Overview

The repository is a Django monolithic web application for a freelance/project-collaboration platform. The codebase is organized into domain apps, each with models, views, URLs, and migrations. The application is primarily server-rendered with Django templates rather than a decoupled frontend-backend architecture.

The repository contains evidence of a multi-app backend structure, including project management, user management, freelancer profiles, work requests, notifications, chat, and ratings. The architecture is monolithic in structure and is not organized as a microservice system.

## 2. Main Applications and Modules

The main Django project is in `devopssite/`, and the repository contains the following major app modules:

- `users`: user identity, authentication, and profile access
- `project`: projects, project status, creation, search, and details
- `skill`: skill taxonomy and project/freelancer skill mapping
- `freelancer`: freelancer profiles, CV handling, portfolios, and related views
- `workrequest`: employment/collaboration requests and status lifecycle
- `rating`: rating records associated with users/projects
- `notification`: notification records, signals, and email dispatch
- `adminpannel`: administrative views for broader management tasks
- `chat`: WebSocket-based messaging implementation
- `portfolio`: portfolio-related app and companion logic

The app-level separation is visible in the folder structure and URL routing configuration in `devopssite/devopssite/urls.py` and each app’s `urls.py` files.

## 3. Responsibility Boundaries

The repository follows a conventional Django responsibility split:

- `models.py`: domain entities and database schema
- `views.py`: request processing, business logic, template rendering, and form submission handling
- `urls.py`: app-level route declarations
- `migrations/`: schema evolution history
- `templates/`: HTML templates for the server-rendered UI
- `static/`: frontend assets used by templates

This structure indicates a modular application rather than a service-oriented or frontend-driven architecture.

## 4. Backend and Frontend Relationship

The frontend is primarily server-rendered HTML generated by Django views. Templates are loaded through Django’s template engine and static assets are served from the static directories. There is no visible React, Vue, Angular, or other independent frontend framework in the current repository.

The backend is therefore the system of record for users, projects, profiles, work requests, notifications, chat state, and AI resume analysis. The repository shows a template-based web application, not a fully decoupled API-first frontend.

## 5. Persistence and Database Interaction

The project uses Django ORM models and migrations for persistence. Database configuration is in `devopssite/devopssite/settings.py`, which configures PostgreSQL via the `django.db.backends.postgresql` engine and environment variables for connection details.

The main visible relationships include:

- `User -> Role`
- `Project -> User`
- `Project -> Status`
- `Freelancer -> User`
- `Freelancer -> FreelancerStatus`
- `WorkRequest -> Project`
- `WorkRequest -> Freelancer`
- `Notification -> User` (sender and receiver)
- `Message -> User` (sender and receiver)
- `Rating -> User` and `Rating -> Project`

This architecture is consistent with a relational database design, and the repository includes migration files under each app to show schema evolution.

## 6. Domain Model

The current domain model is centered on project collaboration and freelance work matching. The principal entities visible in the code are:

- `User` and `Role`
- `Freelancer` and `FreelancerStatus`
- `Skill` and related join models (`FreelancerSkill`, `ProjectSkill`)
- `Project` and `Status`
- `WorkRequest` and `WorkRequestStatus`
- `Message`
- `Notification` and `NotificationType`
- `Rating`
- `Portfolio`

The platform logic revolves around the relationship between project owners/employers and freelancers, with work requests and notifications driving collaboration workflow.

## 7. Main Domain Entities

### User
- Purpose: application user identity and authentication.
- Evidence: `devopssite/users/models.py`
- Relationships: linked to `Role`; referenced by `Project`, `Freelancer`, `Notification`, `Message`, and `Rating`.

### Role
- Purpose: classification of user roles.
- Evidence: `devopssite/users/models.py`
- Relationships: foreign key on `User`.

### Freelancer
- Purpose: freelancer profile data, including CV text and experience.
- Evidence: `devopssite/freelancer/models.py`
- Relationships: linked to `User`; may have portfolio items, skills, and work requests.

### FreelancerStatus
- Purpose: status classification for freelancer profiles.
- Evidence: `devopssite/freelancer/models.py`
- Relationships: used by `Freelancer.id_status`.

### Skill
- Purpose: reusable skill taxonomy.
- Evidence: `devopssite/skill/models.py`
- Relationships: used by `FreelancerSkill` and `ProjectSkill`.

### Project
- Purpose: project record created by a user and associated with a status and skill set.
- Evidence: `devopssite/project/models.py`
- Relationships: linked to `User` and `Status`; may be related to `WorkRequest` and `ProjectSkill`.

### Status
- Purpose: project status classification.
- Evidence: `devopssite/project/models.py`
- Relationships: used by `Project.status`.

### WorkRequest
- Purpose: freelancer request to collaborate on a project.
- Evidence: `devopssite/workrequest/models.py` and `devopssite/workrequest/views.py`
- Relationships: linked to `Project` and `Freelancer`; has a lifecycle status.

### Message
- Purpose: chat message record.
- Evidence: `devopssite/chat/models.py` and `devopssite/chat/consumers.py`
- Relationships: sender and receiver user records; timestamp; deletion flags.

### Notification
- Purpose: system notification for a user.
- Evidence: `devopssite/notification/models.py` and `devopssite/notification/signals.py`
- Relationships: sender, receiver, and notification type.

### Rating
- Purpose: evaluation record associated with a project and users.
- Evidence: `devopssite/rating/models.py`
- Relationships: appraiser, evaluated user, and project.

## 8. External Integrations

The repository confirms the following external dependencies relevant to the architecture:

- PostgreSQL database: configured in `devopssite/devopssite/settings.py`
- Redis Channel Layer: configured in the same settings file for Django Channels messaging
- SMTP email delivery: configured in settings and used in `devopssite/notification/tasks.py`
- Google Drive file download flow: used in `devopssite/freelancer/utils.py`
- OpenAI-compatible LLM API: used in the resume analysis workflow in `devopssite/freelancer/utils.py`

These integrations are implemented as part of the application runtime rather than as separate services in a distributed architecture.

## 9. Important Repository Directories

- `devopssite/manage.py`: Django entry point
- `devopssite/devopssite/settings.py`: project configuration and environment setup
- `devopssite/devopssite/urls.py`: root URL configuration
- `devopssite/templates/`: HTML templates for the user interface
- `devopssite/static/`: front-end static assets
- `devopssite/media/`: runtime media storage
- `devopssite/*/migrations/`: schema history per app
- `devopssite/locustfile.py`: load-testing script

## 10. Architecture Summary

This is a monolithic Django web application with a modular app structure and a template-based UI. It persists relational data through Django ORM models and PostgreSQL, uses Redis + Channels for chat, and uses an OpenAI-compatible API and Google Drive flow for CV analysis. The architecture currently reflects a prototype or bachelor project system rather than a production-distributed deployment architecture.

## 11. Open Architecture Questions

- whether the live system is deployed externally or only run locally;
- whether the database in production matches the local migration state;
